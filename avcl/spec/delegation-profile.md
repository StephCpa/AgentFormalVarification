# 在线能力委派与共享账本详细设计 v0.1

对应详细设计第 17 章、R11、T11 和 P7 的实现基础。本版将委派接入参考内核、PostgreSQL schema v8、认证 HTTP API 和工作流 v0.7 Delegate。子任务监督自动交接与完整 P7 机械证明尚未实现。

P7 的抽象组合核心已在 Lean 中证明，包含任意有限链的权限包含、当前祖先撤销门禁，以及绑定能力额度的共同账本保持。假设、非空实例及实现精化缺口见 [委派形式化规格](formal-delegation-profile.md)；该进展不将完整系统 P7 状态改为完成。

## 权威对象与信任边界

已有 Capability 记录保持原字段与编码，另以 DelegationGrant 记录父引用、独立额度账户、can_delegate、工具集合、效果集合和单调 revoked 位。子能力引用使用随机 256 bit 值。引用不是独立 bearer：使用者还须通过现有认证入口，主体必须与 Capability.subject 相同，租户由服务器凭据定位。

宿主通过 register_subject 建立当前租户下的主体注册记录，通过 disable_subject 永久停用该记录。这个登记表示宿主确认身份，不是客户端提交一个 subject 字符串即可获得身份；生产身份系统和跨服务证明仍未接入。HTTP 不暴露这些宿主管理方法，也不允许客户端指定租户或签发凭据。

默认旧能力不能委派。宿主必须在该能力产生任何操作之前调用 enable_delegation，显式登记根额度和委派许可。禁止事后给已有操作附加额度，以免历史预留缺少新增账户。已登记额度不可被政策发布改写；调整授权应签发新能力并按需求撤销旧树。旧树的未决操作继续保留账务。

## API 与请求绑定

`POST /v1/capabilities/delegate` 要求有效凭据具有 delegate scope。主体、scope、凭据撤销和有效期在取得租户 guard 后复检。

```json
{
  "client_request_id": "grant-child-1",
  "parent_ref": "root-capability-ref",
  "child_subject": "authenticated-child",
  "attenuations": {
    "orders": ["order-a"],
    "tools": ["refund"],
    "effects": ["Write", "Disclose", "ResourceConsume"],
    "max_amount_minor": "60",
    "limit_minor": "80",
    "expires": "800",
    "can_delegate": false
  }
}
```

当前时间仍是测试逻辑时钟，expires 尚不是生产 UTC 协议。金额和时间使用规范十进制字符串；未知字段、重复集合元素、JSON 数字、错误类型、空资源集合均拒绝。集合最多 64 项，正文仍受 64 KiB 限制。

成功返回 child_cap_ref、parent_ref、child_subject 和实际衰减字段；不返回子主体凭据，也不创建 Evidence、Approval、Permit 或退款操作。子主体后续仍需独立资格证据和批准。

幂等键为 tenant/subject/client_request_id，摘要域为 avcl/delegation/0.1，覆盖整个请求。同键异参拒绝。重试返回原引用前复检父链及子能力当前有效性；撤销、停用或过期后不能靠缓存重新获得有效授权。集合顺序目前保留在请求摘要中，改变顺序也属于不同输入。

## 权限衰减与父链检查

1. 父引用必须属于调用主体、当前租户和当前 epoch，且显式允许继续委派。
2. 子主体必须已登记且未停用，不能重复任何祖先主体。
3. 子订单集合、工具集合和效果集合分别是父集合的子集；单次金额上限不能提高，有效期不能晚于父能力。
4. 新子额度不超过任一祖先额度账户及租户根账户的当前可用额度：limit - spent - pending。已 breached 的账户不能新授权。
5. 根深度为 0，最多 8 条委派边。循环、祖先缺失、账户别名、父引用不一致均拒绝。

Prepare 与 Dispatch 都重新遍历完整父链，检查结构、撤销、epoch、主体停用和有效期。可撤销某个子树而不影响其兄弟。租户全局 epoch 增长使所有旧能力失效。并发撤销与准入使用同一个串行化顺序；已准入操作的查询/核对/结算不因后来撤销而丢失。

当前唯一可执行工具是 refund；它需要 Write、Disclose、ResourceConsume 三种效果。可以签发更小效果集合，但该能力不能执行完整退款调用。这个集合检查不等同于完整信息流标签系统。

## 多账户承诺与结算

每次退款同时在以下账户原子预留：租户账户承诺本金加最大手续费，订单账户承诺本金，以及当前能力至根能力的每个委派额度账户承诺本金加最大手续费。所有账户通过后才创建操作、绑定批准并返回许可。

委派时不移动资金，也不预留整份子额度。兄弟额度之和可以大于根额度，因为它们是重叠的消费上限，不是可离线支出的份额。实际 Prepare 始终检查共同根账户。例如根额度 100，两个子额度各 80，两个 60 元操作只能有一个预留成功。父主体自身使用根能力也消耗同一根额度。

额度账户是同一笔费用的多个约束视图，不能跨账户相加来计算真实成本。远端仍只报告租户总费用和订单本金；可信内核从租户费用派生每个祖先账户的累计消耗。远端不能指定本地委派账户费用、少报子额度或改变账户集合。

Unknown 保留所有祖先与子额度的未决承诺。准入前 Abort 同时释放所有预留；父撤销本身不释放。部分结算保留剩余上界。费用超界或终局后新增费用先计入全部相关账户，再标记争议/隔离；不能以子能力已过期或被撤销为由拒收实际成本。

## 持久化与恢复

schema v8 新增 delegation_subject、delegation_grant、delegation_request。能力、额度账户、委派历史、防重记录与审计事件在同一 SERIALIZABLE 事务内写入，并与所有 Prepare/Dispatch 共用 authority_guard。历史 grant 的结构字段禁止修改和删除，revoked 只能从 false 变为 true；请求防重历史禁止修改和删除。

提交前进程退出：子能力、额度账户、防重历史全部回滚。提交后退出：同一请求返回原能力，无重复额度或签发事件。迟到回执继续使用原操作保留的额度账户；原始回执独立落盘后的恢复会重新派生本地额度费用。新迁移保持旧 Capability 编码，v1 至 v7 迁移保留旧操作与义务。

## 工作流 v0.7 Delegate

命令形状为 `{"tag":"Delegate","capability":"c","child_subject":"child","attenuations":{...},"out":"child_cap"}`，attenuations 与 HTTP 委派字段一致。编译时验证闭合字段、十进制数量、集合、子主体字面量和固定退款工具/效果配置；实际父权限、主体登记、剩余额度仍在运行时判断。父 Capability 可重复使用，委派不隐含一次性批准或资金转移。

编译产物将嵌套 attenuation 转为不可变规范字符串，序列化时还原 JSON 对象；修改构建输入或读取到的语义对象不会修改既有 IR。节点输出为 ChildCapability，它是可保留、复制和丢弃的子主体能力引用，不能直接用于父工作流 Prepare、Dispatch 或 Delegate。该类型不能作为输入伪造，Alias 不改变类型。可信宿主负责核对子主体，并将引用作为其工作流的 Capability 输入；运行时复检能力主体。若授权允许继续委派，子主体可以在自己的上下文中委派孙主体。当前执行器信任宿主传入的 subject，尚无面向不可信客户端的工作流启动/引用转交 API；HTTP 委派认证不构成工作流进程隔离证明。

```mermaid
flowchart LR
    P["父主体 Capability"] --> D["Delegate 节点"]
    D --> R["ChildCapability 引用与步骤记录"]
    R --> H["宿主核对子主体并传入引用"]
    H --> C["子工作流 Capability 输入"]
    C --> A["Prepare / Dispatch 复检主体与父链"]
    A --> B["共同根账户及各级额度"]
```

静态效果为 Read/ResourceConsume，分支效果取并集，合流后引用只有在两侧均定义时才可用。命令本身不执行 Spawn，不启动子进程，也不创建子任务完成义务。Drop 只删除局部变量，不撤销已经持久签发的子能力。

持久节点的请求键以 avcl/workflow-delegate/0.7 域绑定 run_id、工作流摘要和 node_id；核心委派防重还绑定 tenant/subject。政策摘要与逻辑时钟在节点执行时复检。子能力、额度、委派防重记录、审计事件、引用环境、步骤和 pc 同一事务提交。并发 worker 不重复签发，提交前进程退出全部回滚，提交后退出从下一节点续办。步骤保留 child_cap_ref、child_subject、parent_ref，便于宿主传递引用与审阅。

已完成运行的相同重放返回历史步骤，不重新签发或延长子能力。返回的历史引用仍须在实际使用时通过当前父链、撤销和有效期检查。内存执行器仅提供进程内工作流缓存及内核委派请求防重，不提供持久检查点保证。

v0.4/v0.5/v0.6 都拒绝 Delegate；冻结旧样本继续按原字节和摘要恢复。新增测试覆盖类型混用、不可变配置、分支、内存执行、真实提交边界进程退出、并发节点、政策/撤销/时钟变化、父主体冒用拒绝、子与孙主体正确执行，以及父撤销后子 Unknown 的持久核对。

delegation-demo 现在输出父委派和子退款两个工作流 IR，以及父/子各自执行报告：父程序签发两个子能力后 Finished；一个子程序预留 60，另一个因共同预算不足 Halted；前者丢回执并在父撤销后继续 Reconcile，最终实际费用仍为 60。这些程序完成状态不替代任务级 Close。

## 验证与边界

单元测试覆盖各维度越权、身份、深度、循环/缺失父链、费用上界、兄弟/父子共享预算、撤销与 Unknown、部分结算和超界、额度不可追溯附加、政策不可改写额度。真实数据库与 HTTP 测试覆盖并发签发、兄弟预留竞争、撤销/派发竞态、凭据和 scope、进程退出、防重恢复、原始回执恢复及历史字段不可扩张。

独立有限模型采用两个子能力、每个额度 2、共享预算 3、每次费用 2；正确模型有 40 个状态、60 条边，无所查反例。去掉共享预算门禁得到两个 Prepare 的超额轨迹；去掉祖先撤销复检得到 Prepare → RevokeAncestor → Dispatch 反例。该模型不涵盖费用、崩溃、通用权限包含关系，不是 P7 全证明或 SQL 精化证明。

完整验证生成 delegation-demo/execution-report.json：两个子额度、第二次预留被拒绝、丢回执、父撤销、重载和恢复结算；真实费用只按独立远端效果计一次。

首轮完整回归保存在 `evidence/20261025T182417.782515Z`：158 项数据库测试中 3 项迁移夹具失败，原因是模拟降级时遗留 v8 表，重新升级触发 DuplicateTable。已在测试自有 schema 内补齐旧版本形状还原；生产迁移仍拒绝重复对象，失败证据保留。最终通过状态以之后的新验证报告为准。

仍待实现：委派历史/主体数量容量限制、通用工具与标签、子任务父子因果字段及监督自动交接、生产身份/数据库角色/出口隔离、可信时间、一般组合定理和实现精化。当前在线共享账本不承诺离线 escrow、跨数据库预算分配或生产吞吐量。
