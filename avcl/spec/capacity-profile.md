# 容量背压与未来义务预留

依据详细设计第 4、15.3、23 章，PostgreSQL schema v4 将容量策略持久化并与 prepare、工作流创建共用租户 guard。它控制活动工作准入，不限制历史证据总量，也不丢弃已经发生的现实事实。

## 三类容量

默认每租户三项限额均为 1000，可由宿主 `kernel.trusted.set_capacity(operations, obligations, workflows)` 显式调整。参数必须为 0..1000000 的整数；0 可用于在无相应存量时关闭新增准入。调整不能低于已承诺的使用量，不能借改配置删除旧实例。普通 Agent 没有容量配置入口。

|限额|当前使用量|
|---|---|
|max_operations|结算尚非 Final 的操作，包含 Prepared、在途、Unknown、费用未终局及 Disputed|
|max_obligations|未终局操作 ID 与未履行核对义务操作 ID 的并集大小；每操作保留一个未来核对槽位|
|max_workflows|Running、WaitingIO、WaitingCapacity 的持久工作流数量|

这里的“一个未来槽位”对应当前每操作至多一条 O-Reconcile 的实现。通用语言若允许一个操作产生多种义务，必须按其已编译上界改为向量预留，不能直接沿用本计数。

在 Prepare 时即检查操作和未来义务余量。只统计当前 Unknown/Open 会放行多个 Prepared，再在同时超时后超过义务上限，因此本实现不采用该算法。所有检查位于认证/绑定检查之后、状态变更之前，且与账本预留同事务。直接 API 与工作流本地内核路径都使用同一门禁。

相同请求或业务键的幂等读取在满额时继续返回已有操作；新操作返回 OPERATION_CAPACITY_EXCEEDED。未知操作转 Unknown、租约回收和义务建立不需要重新申请槽位。准入前 Abort 或正常终局结算可释放活动容量，历史记录仍保留。人工确认转交只改变责任，未终局操作仍占槽位，不会释放预算或为新危险操作腾出容量。

## 工作流等待

创建新的持久工作流达到限额时拒绝 WORKFLOW_CAPACITY_EXCEEDED。已有 run 的重试不新增实例。

已创建工作流在 Prepare 遇到操作容量不足时进入 WaitingCapacity，而不是 Halted。失败事务不提交新操作、批准消费、引用环境或 pc；首次背压记审计事件，重复尝试不重复追加相同背压事件。容量释放后，`resume` 在原位置重新检查现时授权/政策/预算，成功后清除等待诊断。等待中的工作流本身仍占工作流槽位，避免候选队列无限增长。当前没有自动公平唤醒调度器，宿主需显式续办。

## 满额下保留的通道

读取状态、已有操作准入及处理、取消 Prepared、原始观察落盘、结算、只读核对、监督租约恢复和已确认责任交接均不因容量满而禁用。写权限撤销后，已授权的固定只读模拟核对路径仍可完成旧操作。这些通道不会新建未经预留的危险操作。

外部违约可能在原来已终局的操作上带来新的费用/争议；这类事实不能被容量 CHECK 回滚。系统先记录真实费用和事故、保留新增义务并隔离，再以 `over_capacity=true` 报告越限、阻止新准入。因此容量上界是正常准入承诺，不是“即使外部违约也绝不记录第 N+1 条现实事件”的保证。

`kernel.capacity()` 返回三项限额、活动操作数、预留义务槽位数、当前未履行义务数、活动工作流数、可用余量和越限标志。无凭据或政策密钥。该查询用于宿主监控，完整服务级遥测和认证出口仍需实现。

## 迁移与证据

`004_capacity.sql` 将 v3 升级为 v4，保留所有操作、义务和工作流检查点。既有实例多于默认值时，将初始限额提高到至少覆盖存量，不删除存量以满足默认值。正式调整仍走受控配置事务。

集成测试覆盖最后一个槽位的连接竞争、预留未来义务、满额幂等重试、交接不释放容量、满额仍可核对、配置下调失败不变性、工作流等待/续办、真实迟到费用越限仍落盘和已有检查点升级。默认值及大规模存量迁移的性能尚未完成生产压测。

独立有限模型 `models/capacity_model.py` 枚举两个操作、容量一、单义务的全部可达状态，并保留两个错误门禁的反例：只数现有义务，以及交接就释放槽位。模型不调用容量实现函数，结果保存在 capacity-model.json。它不含收费、数据库崩溃或适配器违约，也不是 Python/SQL 的精化证明。

仍需完成收费维护预算、容量公平调度、受信配置身份、历史归档/存储配额、通用多义务编译上界，以及设计中的 10000 在途操作恢复扫描性能验收。
