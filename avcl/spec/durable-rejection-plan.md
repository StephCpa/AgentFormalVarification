# 持久拒绝记录事务设计

序号分配已由 schema v10 的[事务计数行](audit-counter-profile.md)落实；本文其余全系统验收目标保持不变。

依据详细设计 §2、§3.3、§20。本文保留最初的方案和全范围验收目标。认证网关现已实现，行为、配额和验证边界见[实现规格](durable-rejection-profile.md)；其余入口、归档、部署隔离和完整审计协议仍未完成，不代表 M1 发布。

## 事务边界

对已认证、已绑定租户且已取得 authority_guard 的写操作，在现有 SERIALIZABLE 外层事务内建立业务 savepoint。成功时按现有路径保存业务状态、事件和 outbox 并提交。业务 Reject 时回滚 savepoint，丢弃被业务函数修改的内存内核，从回滚后的数据库状态重建；在仍持有 guard 的外层事务中只写拒绝事件及审计序号，提交后才向调用者重新抛出原始拒绝。

序号来自事务内租户行更新，不使用无法随事务回滚的数据库 sequence；失败业务中的序号分配随 savepoint 一同回滚。拒绝事件记录当次 guard 内实际观察的 policy_digest、epoch 和 operation_revision，不能在释放锁后用新政策冒充原拒绝依据。业务账本、许可、批准、幂等表、业务 outbox 和操作 revision 必须与调用前一致。可信时钟是否推进须作为单独状态规则明确并验收，不能混入“仅审计变化”的断言。

业务回调不得执行外部网络效果；Send 仍先提交发送意图，提交后执行 I/O。数据库连接故障、序列化冲突和崩溃不是业务 Reject：事务失败应由原重试/恢复策略处理，不能伪造一个已成功保存的拒绝事件。若审计提交失败，不声称已记录，不返回可误导为已持久化的 receipt。重试必须明确 attempt/event ID 与业务幂等键的区别，不能因先前一次拒绝永久屏蔽后来可允许的请求。

## 事件上下文与信任

入口显式传入经宿主认证的主体/租户、动作类别、规范请求摘要和可披露操作引用。不得从闭包、用户自报 actor 或任意原始 JSON 推断可信上下文。字段至少包括 event_id、tenant_sequence、event_kind=ActionRejected、actor、操作标识及 revision（不存在时为空）、request_digest、policy_digest、epoch、code、requirement_ids、可信时间及可核验因果/证据引用；拒绝的 budget delta 为零。

未认证、未知租户、时钟失效、guard 获取前或内核无法加载的错误不能伪装成已认证租户事件。若要记录这些入口失败，需要独立宿主安全日志协议，分别定义主体未确认、时间未确认和持久性状态。面向无权调用者的返回继续遮蔽对象是否存在；内部审计的可见性按租户权限控制，不把内部条款和来源泄露到 HTTP。

## 容量、恢复和验收

实现前须选定容量与保留策略，约束主体频率、记录尺寸及 tenant 日志配额，防止攻击者通过拒绝洪泛耗尽数据库。达到容量时必须明确服务行为；聚合计数和采样不能冒充逐次拒绝持久记录。原始凭据、请求全文和任意异常 repr 不入事件。

验收至少覆盖：预算/仿射/政策/绑定拒绝；业务部分变更后 Reject；拒绝提交前后 kill；提交响应丢失后的重试；序列化重试；两个进程并发成功与拒绝；重连读事件与连续序号；旧政策下拒绝与新政策切换的先后顺序；未知租户与无权对象的遮蔽；磁盘/配额失败；审计访问隔离。业务表不变和仅新增审计记录必须分开断言，保留现有预算原子性检查的强度。

实施顺序：先定义可信请求上下文和事件 schema，再实现 savepoint/guard 协议及失败策略，最后接入入口、回放/导出和容量控制。仅调用 `_event` 后又抛出 Reject 会一起回滚；在原事务回滚后另开事务补日志也不能自动满足同一政策快照语义。这两种捷径不作为完成方案。
