## 双进程证据的含义

`integration/test_m1_processes.py` 在每个用例创建的随机测试 schema 上持有 authority_guard 行锁，再启动两个独立 Python 解释器。通过 `pg_stat_activity` 观察两个不同 backend PID 的 active/Lock 状态，确认两条阻塞链均到达测试持有者；此时两个宿主进程仍存活，才提交测试锁并收集结果。证据包含真实进程 PID、应用名、数据库等待、阻塞关系和最终账本/效果事实。

三项用例分别覆盖同一许可并发消费、70/60 竞争 100 预算、相同 prepare 请求防重复预留。第一项的两个调用都可成功返回同一操作，这属于协议允许的幂等重试；成功准入事件仍只有一次。远端效果在父进程的独立模拟服务中重放核对，不声称测试了两个网络发送进程或真实支付接口。

首次运行暴露的是测试夹具的 Windows venv 启动器 PID 差异，并非协议失效。夹具改为直接启动实际解释器并明确传入当前依赖路径，随后核对返回 PID 与所拥有的子进程句柄一致。清理只终止本用例创建且仍存活的子进程，数据库仅清理本用例的随机 schema。

## 可复现入口与报告边界

```powershell
# 在 avcl 目录；使用现有私有 PostgreSQL 测试实例
.\.venv\Scripts\python.exe scripts/local_postgres.py start
.\verify.cmd --m1 --smt
.\.venv\Scripts\python.exe scripts/local_postgres.py stop
```

`--m1` 要求真实数据库及固定版本/持久化设置，执行 `scripts/m1_checks.py` 中列明的 24 个检查，其中 6 个使用 PostgreSQL，3 个包含双进程重叠；本轮新增 5 项求值预算检查。它保存逐项测试 ID/需求编号、成功/失败状态、来源摘要和现场观测；类初始化失败也留存，缺失或跳过用例不能算通过。`m1-targeted/report.json` 的 `suite_passed` 只描述这组命名检查，`release_decision=not_issued` 不授予发布结论。

完整 `verify.cmd` 另行运行原有单元测试、有限模型和 Lean 构建；`--smt` 增加离线查询。`--m1` 不等于 `--postgres` 全套集成测试：报告用 `postgres_full_suite_requested` 区分全部数据库测试与本轮定向检查。历史全量数据库记录仍独立保留，不借其数量扩大本轮覆盖。
