# 事务审计序号 v0.1

对应详细设计 §20.3。schema v10 引入每租户一行的 `audit_counter(tenant_id,last_sequence)`，不使用 PostgreSQL sequence/nextval。此实现覆盖所有经过 PostgresKernel 的事件分配，包括成功动作、控制面、工作流、监督以及已接入的认证拒绝；它不扩大拒绝日志的入口覆盖范围。

## 分配和提交

租户 authority_guard 仍是事务第一把业务锁。持久内核的 `_event` 使用宿主局部回调执行 `UPDATE audit_counter SET last_sequence=last_sequence+1 ... RETURNING last_sequence`，用返回值构造 Event。回调及连接不序列化，不是可传递权限。纯内存参考内核继续使用本地连续编号，不声称具备数据库持久性。

分配与业务 SQL、事件插入处于同一事务。Reject、序列化重试、崩溃或保存点回滚同时撤销计数；认证拒绝回滚业务保存点后重新加载基线，再分配并保存其自身事件，复用未提交的序号。已提交事件的序号不会因响应丢失而回收。

加载时同时检查计数行、事件条数、表中 sequence、载荷 Event.sequence 及精确整数类型，必须构成 1 到 last_sequence 的连续投影。缺失/超前计数为 CORRUPT_AUDIT_COUNTER，错误投影或缺口为 CORRUPT_AUDIT_SEQUENCE；不自动补日志、重编号或修复计数。

保存只 INSERT 新增后缀，不再 upsert 全部历史。内存历史必须保留加载时的不可变前缀，新增编号必须连续，计数必须等于全部事件数，否则拒绝。重复保存同一内核且没有新事件不会新增行或分配号。只读回调不得改变事件或计数；意外分配也会使事务回滚。

前缀比较现采用冻结的规范编码，避免 Python 的 `True == 1` 掩盖类型改变；事件 details 必须为不可变、有序、唯一的字符串键值。宿主[审计快照](audit-export-profile.md)另行保留原始 payload 文本，并提供分页链和离线检查点校验。

数据库插入触发器同时检查序号已经分配，以及表列和载荷的 Event/sequence 投影一致。旧写入器跳过计数行追加新序号会失败，而不是制造计数落后的历史。该触发器不替代受信宿主、事务提交检查及数据库权限管理；能任意更新计数、禁用触发器或直接控制数据库的主体不在保证范围内。

计数范围为 0 到 2^63-1；耗尽或分配时缺失行返回 AUDIT_SEQUENCE_UNAVAILABLE，不能回绕。计数增长不依赖现有历史长度来分配，但当前适配器仍加载完整历史用于完整性检查；没有因此声称解决大租户吞吐或内存规模问题。

网关将计数耗尽、审计历史/投影损坏及历史改写错误作为 HTTP 503 不可用返回，不能要求调用者通过修改正常业务参数来绕过。加载阶段无法建立可信历史时不尝试追加拒绝事件。

## 升级与运维

010 迁移在同一事务中按 authority_guard、audit_event 顺序取得 ACCESS EXCLUSIVE 表锁，检查每租户旧序列从 1 开始且 count=max、载荷投影一致，再按已提交末尾初始化计数；空租户从 0 开始。保留全部旧事件字节，不补造 event_id，不把旧拒绝改标成新协议记录。验证失败会回滚新表及版本更新，保持原 schema 版本。

升级应在维护窗口停止旧版本写入器，并先保留可恢复备份；迁移锁保护初始化期间的数据，但不承诺旧二进制可在升级后继续服务或支持在线混合版本。未分配事件的数据库拒绝只是附加防线，不能代替版本切换流程。本实现没有提供降级迁移、清理历史或计数重置接口。

## 验证

`integration/test_audit_counter.py` 覆盖分配先于插入、重复保存、保存点回滚后的拒绝事件、prepare 提交前后进程终止、旧历史改写/删除/伪造后缀、计数缺失/篡改、表与载荷投影、v9 原字节迁移、损坏历史拒绝升级、计数耗尽、数据库插入失败、新租户隔离、旧写入器以及只读误分配。

既有 v1—v9 升级测试检查最新计数；双进程测试在观察实际锁等待后检查 count、max(sequence) 和 last_sequence 相等，现场数值写入 M1 定向证据。完整回归还覆盖原有任务、监督及拒绝审计。测试和事务设计不是 Python/SQL 的机械精化证明；完整事件因果链、外部归档及部署角色隔离仍未完成。
