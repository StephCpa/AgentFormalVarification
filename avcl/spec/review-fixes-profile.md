# 3e5c63f 审阅问题修复规格

日期：2026-10-26。对应审阅报告 F1—F4；原始设计与历史验证证据不改写。各项修复的运行结果以新生成的 `evidence/*/verification.json` 为准，M1 门槛仍需逐项验收。

## F1 终局知识保持

`TrustedPlane._observe_trusted` 先执行身份、绑定、费用维度、重复 ID、结果矛盾和累计费用下降检查，并登记新证据。若已有结算为 Final、新观察的执行结果相同且所有账户累计费用与已入账费用相同，则新证据被已有终局知识涵盖：记录 `ObservationSubsumed`，保持操作、费用、零预留和 Final 不变。

这一规则同时适用于费用上界未用尽和恰好用尽的情况。数据库继续调用同一内核；任务当前投影、历史关闭回执、Done outbox、已解决义务及已释放容量因此保持一致。原始回执和鉴权事件仍追加保存。已有 Disputed 不自动清除；真实新增费用、矛盾终态、同 ID 异内容及下降累计值继续走原有事故路径。

规则不以 `observed_at` 大小直接丢弃证据。本次只处理相同结果、相同累计费用的冗余事实，不将更低累计费用或不同效果状态一概认定为无害旧消息。多来源事实版本与更广的观察偏序仍待定义。

## F2 工作流发送所有权

保留 Dispatch 为本地准入、Send 控制外部效果的语言语义。

持久层复用 schema v3 已存在、在 Prepare 事务中插入的 `workflow_operation`，关联 `workflow_run` 的冻结摘要，得到 `(tenant, operation_id, subject, run_id, workflow_digest)` 归属。每次恢复内核重建归属映射；新 Prepare 同事务更新映射与表。内存执行器也将归属登记在内核而非某个 sender 的私有缓存中。

通用 `claim_outbox` 排除所有工作流所属操作，无论运行是 Running、Finished、Halted，还是已重启、失去 worker。工作流自身在解析当前可执行 Send 节点之后建立宿主局部发送上下文；统一 `admit_attempt` 检查该上下文与归属一致。仅传入 run_id、node_id 等字符串不能授权。检查、发送尝试和 `workflow_io` 节点意图在同一数据库事务中提交；提交之后才允许网络 I/O。发送审计包含归属、主体、run_id、node_id、workflow_digest、请求 binding、worker 和 generation（后两项在持久路径）。上下文退出时清除。

归属记录是持久权威；局部上下文只表示宿主解释器当前已解析到的节点，不作为可序列化能力。该机制不声称防御能任意修改 Python 内部对象、调用私有函数或直接改数据库的宿主。

本次不新增 schema、不改变旧 Operation 的序列化字段，也不把旧 Pending 行批量重写成未发送。旧工作流 Pending 行因既有归属自动受到新领取门禁约束；已在途、未知或有实际效果的操作保留账本与核对路径。Pending 仅表示发送队列阶段，不再单独意味着通用消费者有权领取。direct 操作继续使用通用发送器。

没有隐式或显式移交实现。若需要交接，必须另行定义持久协议；Finished、超时和恢复均不转让发送权。监督器只读核对与回执应用不受发送权门禁阻断。原有等待期限仍可使未发送操作进入 Unknown/核对，不能因此释放预算或授权发送。

## F3 累计费用数值域

请求的本金与最高手续费仍各为 0 到 `10^18-1` 的规范十进制字符串，本金必须正数。回执的累计费用使用独立 `cumulative_cost` 解析器，范围为 0 到 `10^19-1`，不接受符号、前导零、指数、小数、布尔值或 JSON 数字。两个合法请求分量之和至多为 `2*(10^18-1)`，严格包含在累计费用域内。时间仍使用原有时间域。

回执签发和解码均检查该域；超过操作承诺但在累计域内的真实费用仍可进入账本事故处理。PostgreSQL numeric 和原有存储编码可保存这些整数，不需要改变金额列或原请求摘要。委派账户继续由已验证的租户累计成本映射，而非接受远端提供的新账户维度。

这是本地 `avcl/receipt-envelope/0.1` 实现的数值域修正；字段、MAC 域和历史小额签名不变。旧实现不能正确处理新增可解码的大额值，部署新适配器时必须同时更新验证端；不能据此声称与第三方实现自动兼容。旧大额原始回执如果尚未应用，可通过新版解码恢复；若已经登记拒绝结果，应重新提交真实回执，由正常应用事务重试，不删除拒绝历史或自动解除隔离。

更长的费用仍明确拒绝为 `INVALID_CUMULATIVE_COST`。数据库保存原始输入及拒绝记录，保留未决承诺；这一错误不表示未知巨大费用已准确入账。正常协议数值闭合与任意异常事实的人工处置是不同边界。

## F4 历史运行回放

内存 `_runs` 保存提交摘要、结果和历史合约摘要。已有 `(subject, run_id)` 在宿主历史快照下加载程序、规范化引用、值和故障计划并重算提交摘要；完全相同则返回旧结果，不同仍拒绝 `WORKFLOW_RUN_CONFLICT`。缺失历史快照拒绝 `WORKFLOW_HISTORY_UNAVAILABLE`，不回退当前合约。

新运行仍绑定当前合约；旧合约不成为新动作的授权。政策升级、Halted 结果和既有外部效果不会被回放重新执行。内存缓存仍不跨进程持久化；持久后端继续使用数据库历史合约快照。

## 验证链与范围

- `tests/test_review_regressions.py`：签名回执乱序及重复、真实增费/矛盾反例、工作流归属、合法聚合金额边界、规范编码、政策回放与冲突检查。
- `integration/test_review_regressions.py`：任务/账本/outbox/义务/容量联动，原始回执提交后崩溃，Send 意图提交前后崩溃，true/false 分支与普通 sender 并发，重开后发送权及历史回放。
- `models/review_composition_model.py`：两个独立有限模型。观察模型显式生成两个事实并允许分别投递和重放；发送模型组合分支、归属门禁、发送意图和远端效果，保留重启与回滚步骤。错误合并及无归属发送门禁两个变体均须产生反例。
- `tests/test_review_models.py`：将观察模型每条边置于一条最短代表前缀之后回放到内存实现，比较独立远端成本、spent、pending 和 Final；不等于覆盖全部具体历史。

验证脚本增加 `review-composition-model` 阶段，不修改既有 Lean 定义来容纳错误转移。正常模型不含矛盾事实；事故路径由测试独立验证。数据库交错、真实适配器、公钥身份、主机隔离和完整机械精化不由这些模型证明。
